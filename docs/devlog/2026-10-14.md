# 2026-10-14 Tiny Week Development Log

## Work Summary

아이폰 홈 화면 웹앱이 배포 후에도 구버전을 계속 표시하는 문제를 줄이기 위해 자동 업데이트 확인과 안전한 화면 교체를 구현했다. 사용자 기록을 보존하고 작성 중에는 적용을 미룬다. 다른 웹앱에서도 참고할 수 있도록 업데이트 흐름과 배포 규칙을 문서화했다.

## Work Completed

- `app-updates.js`에 실행·복귀·온라인 전환 및 열린 화면의 60초 주기 확인을 추가했다. HTTP 캐시 우회, 중복 요청 방지, 실패 후 재시도와 활성 버전 조회를 연결했다.
- 입력칸 포커스, 문자 조합 입력, 편집 모달, 백그라운드 상태에서는 자동 새로고침을 미룬다. 편집 종료 후 적용하며 같은 버전 전환에서 갱신이 반복되지 않도록 보호한다.
- 자동 적용 직전 보던 주를 세션에 기록해 복원한다. 기존 로컬 식단·영화·메모와 회전 설정은 유지한다.
- 버전을 `app-version.js`의 `tiny-week-v13`으로 통합했다. 서비스 워커와 화면이 같은 값을 사용한다.
- 서비스 워커는 필수 파일 20개를 받은 뒤 버전 파일 일치까지 확인하고 활성화한다. 현재 버전 캐시만 조회하고 캐시 삭제를 `tiny-week-` 접두사에 한정해 다른 앱 캐시를 보존한다. 실패한 HTTP 응답은 캐시하지 않는다.
- `docs/pwa-updates.md`에 적용 조건, 배포 절차, 초기 전환 한계와 다른 앱에서 바꿔야 할 항목을 기록했다.

## Decisions

- 상시 배너나 버튼을 추가하지 않고 안전한 시점에 자동 적용한다. 영화 편집 창은 저장 전 내용이 있으므로 닫힐 때까지 기다리고, 메모도 입력 포커스와 한글 조합이 끝나기 전에는 화면을 바꾸지 않는다.
- 파일 묶음이 완전히 준비된 버전의 캐시를 사용한다. 배포 중 파일 누락이나 버전 변경으로 설치가 실패하면 기존 앱을 유지한다.
- 버전은 한 파일에서만 올리도록 해 화면과 워커의 값이 어긋나는 실수를 줄였다. 향후 코드·정적 파일 배포에서도 반드시 버전을 올려야 한다.
- 기존 v12 화면에는 새 이벤트 처리 코드가 없으므로 강제로 화면을 교체하면 작성 중 내용을 잃을 수 있다. 첫 전환은 새 워커 설치 후 페이지를 한 번 다시 불러오는 방식으로 유지한다.

## Current Status

JavaScript 네 파일의 구문 검사 및 로컬 Chrome/Playwright 업데이트 전환 검증을 완료했다. 실제 서비스 워커와 10분 HTTP 캐시 헤더를 사용하는 로컬 서버에서 버전 파일만 바꿔 v13→v18 배포를 모사했다.

- 입력·문자 조합 및 영화 편집 중 적용 대기, 저장·포커스 해제 후 자동 적용을 확인했다. 저장 기록, 보던 주, 회전 설정과 다른 앱 캐시가 보존됐다.
- 백그라운드 적용 대기와 복귀 후 적용, 오프라인 재진입, 필수 파일 503 설치 실패 후 온라인 재시도, 설치 중 버전 불일치 거부와 정상 재시도를 확인했다.
- 잘못된 이전 버전 화면을 계속 제공해도 추가 자동 갱신은 한 번으로 제한됨을 확인했다. 처음 테스트에서는 브라우저 HTTP 메모리 캐시가 인위적인 구버전 파일을 가려서, 테스트 파일에 별도 URL을 사용해 실패 상황을 정확히 재현했다.
- v12 캐시를 설치한 별도 브라우저 세션에서 v13 전환과 기존 메모 보존을 확인했다. 이 초기 전환은 새 워커 설치 후 한 번의 페이지 재진입이 필요했다.
- 2048×1152, 1280×800, 가로 844×390, 회전 보기 390×844에서 기존 영화·메모 영역 표시와 가로 넘침을 확인했다. 앱 JavaScript 실행 오류는 없었다. 기존 누락 인접 연도 데이터 조회와 의도한 설치 실패는 검증 과정에서 별도로 구분했다.

Browser 플러그인이 없어 번들 Playwright와 설치된 Chrome을 사용했다. 검증 스크립트와 화면 캡처는 프로젝트 밖에 두었다. 커밋·푸시·배포는 진행하지 않았으며, 실제 아이폰에서의 첫 전환과 후속 자동 업데이트는 아직 확인하지 않았다.

J님이 v14 적용 후 제공한 Safari·홈 화면 웹앱 사진에서 메모칸이 잘리고 입력 후 날짜가 숨는 현상을 확인했다. 정사각형 이미지의 불필요한 상하 여백을 줄이고, 회전 화면의 안전 여백과 실제 달력 높이에 맞춰 행을 배분하도록 수정했다.

## Work Completed - 식단 여백과 회전 화면 높이

- 식단의 상하 패딩 8px를 제거했다. 칸 너비와 식단 높이 상한에 맞춰 행 높이를 정하고, 이미지 비율과 `contain` 표시를 유지한다.
- 회전된 화면에서는 아이폰의 물리적 안전 여백을 대응하는 좌우·상하 방향으로 바꾼다. 식단·영화 모달에도 같은 방향 매핑을 적용했다.
- 달력 컨테이너의 실제 높이·너비를 기준으로 식단 행 높이를 계산한다. 날짜·공백의 달·영화 두 칸·메모의 높이를 먼저 확보하고 남는 공간에서 이미지를 표시한다.
- 날짜 열의 자동 최소 높이를 해제하고, 달력을 숨은 스크롤 컨테이너로 만들던 `overflow: hidden`을 `clip`으로 바꿔 메모 포커스가 날짜를 위로 밀지 않도록 했다.
- 평소 메모 글자 12px는 유지한다. 터치 기기에서 메모에 포커스가 있거나 영화 입력칸을 사용할 때는 16px로 표시해 작은 글자에 따른 입력 자동 확대를 줄이도록 했다.
- 배포 버전을 `tiny-week-v15`로 올려 CSS 변경을 기존 설치에도 전달할 수 있도록 했다.

## Decisions - 식단 여백과 회전 화면 높이

- 원본 파일을 자르거나 비율을 바꾸지 않는다. 상하 여백만으로 부족한 경우에는 식단 영역을 더 작게 표시하고 날짜·영화·메모를 유지한다.
- 회전 상태에서 세로 화면의 아래 안전 여백을 달력 아래에 그대로 적용한 것이 가용 높이를 줄였다. 여백 자체를 없애지 않고 회전 방향에 맞춰 위치를 바꿔 화면 가장자리 보호를 유지한다.
- 입력 후 날짜가 숨는 것은 숨은 스크롤 컨테이너가 포커스를 따라 이동하는 현상으로 Chrome에서도 재현됐다. 강제로 스크롤을 반복 초기화하는 대신 넘침을 없애고 컨테이너를 스크롤하지 않도록 바꿨다.

## Current Status - 식단 여백과 회전 화면 높이

로컬 Chrome/Playwright에서 데스크톱 2048×1152·1280×800, 가로 844×390·780×360, 회전 390×797·339×693·339×734·320×740 및 Safari 모사 339×630의 총 9개 조건을 검증했다. 안전 여백 0·21·34·47px와 115% 확대에 준하는 유효 뷰포트를 모사했다. 모든 날짜·영화·메모 표시, 영화 글자 잘림 없음, 가로 넘침 없음, 메모 입력·포커스 해제 후 달력 스크롤 위치 0, 저장 및 영화 편집 동작을 확인했다.

Browser 플러그인과 실행 가능한 WebKit 브라우저가 없어 설치된 Chrome을 사용했다. 실제 아이폰의 Safari 115% 및 홈 화면 키보드·닫기 후 복원은 아직 미확인이다. J님의 추가 요청에 따라 화면 수정·v15 버전 파일·개발 로그 세 파일을 함께 커밋·푸시해 GitHub Pages에 배포한다.
